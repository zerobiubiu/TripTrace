## Platform

web

## Users

- **主用户**：需要记录每日出差路径与里程的业务人员（跑客户、送货、跑厂区），典型场景是在**车间、厂区、客户楼下用手机单手记一笔**，之后回到办公室用桌面浏览器补齐或核对。
- **同一产品下的其他用户**：使用者的同事，各自独立账号、**数据相互隔离**（彼此不共享、不互相查看）。
- **明确否认的假设**：目前没有「看别人数据」的角色（主管/财务）。若将来需要汇总他人里程，那是新的面与权限模型，不要在没有确认时替用户发明。

## Product Purpose

把原本写在文本里的行程账（日期 + 节点链 + 里程）搬进随手可填的应用：打开就是今天、节点按历史补全、里程自动带出、总里程可独立填写，月末不再手算。
成功的样子：**一次行程 30 秒内录完，且历史数据随时可汇总、可导出**。

## Positioning

用「**节点链 + 历史路线记忆**」而不是「起点 → 终点」记里程：常跑的路线（家 → 圣润 → 天九 → 圣润 → 家）第一次手填之后，后续点一下就能带出全部分段与总里程；并且**总里程可以先于分段存在**——只记得总数也能入账。

## Operating Context

- 记录发生在路上：厂区、车间、客户现场；一只手操作，屏幕在户外光线下看。
- 补录与核对发生在桌面浏览器：看月度汇总、导入历史文本、导出备份。
- 历史存量是**纯文本**，写法由用户形成习惯：`9.28`、`家，依剑，爱克森，圣祥小镇，圣润 57 公里`、`单次25km`、`7.1-7.2` 区间、`203 公里` 小计、`------` 分隔线。产品必须能解析这种写法并导入（含预览与去重）。
- 术语沿用用户自己的语言：节点、分段里程、总里程、行程、常用路线、导入。

## Capabilities and Constraints

已实现：注册/登录（长期登录态、多设备独立）、同一天多条行程（节点链 + 分段可选 + 总里程 + 备注）、历史节点补全、分段与整条路线建议、常用路线一键填入、月/年汇总与高频路段、历史文本导入、JSON 导出、改密清理其它会话。

技术与运营约束：

- 运行时：Cloudflare Workers（Hono）+ D1 + KV；前端 React SPA 由 Pages 托管，API 与前端**同域名、两个路径**。
- 前端组件库：**MUI（Material UI）v9**（含 emotion 样式引擎与 @mui/icons-material）。因 MUI 的样式在运行时注入，**构建期降级管线对组件库自身 CSS 无效，MUI 的官方基线就是本产品的真实兼容地板**。
- **浏览器支持基线（2026-10-08 修订，用户明确选择）**：Chrome ≥117 / Edge ≥121 / Firefox ≥121 / Safari ≥17（macOS 与 iOS）。微信内置浏览器**仅在系统内核满足该基线时**在支持范围内（iOS 17+、Android WebView ≥117）；**旧机型与旧微信内核已不在支持范围** —— 这是为换取组件库与长期可维护性而做的取舍，取代此前「必须支持微信内置浏览器与旧机型」的绝对要求。
- 密码：PBKDF2-SHA256，迭代受 workerd 10 万次上限约束；**无邮箱找回**，忘记密码只能由管理员在 D1 侧重置（属于已接受的取舍）。
- 安全：严格 CSP（无内联脚本/内联样式），改前端时不能用内联写法绕开。
- 体积：随组件库引入，首屏 JS 体积会高于此前的 80 kB（gzip）；导入/汇总视图按需懒加载以摊薄首屏。
- 计时口径：日期取用户本地时区（不存时区）；里程以公里为唯一单位，保留两位小数。

**方向（已确认、尚未实现）**：产品要从「里程记录」扩展为「**出差台账**」——记录费用、客户、备注并汇总。范围、字段与汇总口径尚未确定，属于后续 shape 的输入，不要在实现里自行发明。

## Brand Commitments

- 名称：**途迹 / TripTrace**（页面标题「途迹 TripTrace · 出差行程里程记录」；图标为渐变蓝→青的「路线 + 两个节点」SVG：`apps/web/public/icon.svg`）。

## Product Principles

1. **录一笔要快**：默认今天、历史补全、一键沿用；任何字段都不强制填齐。
2. **总里程优先于细节**：总里程是账的口径，分段是可选细节；两者不一致时提示但不阻止保存。
3. **用用户的语言**：节点名、路线、记录写法都由用户决定（可中文、可沿用原有文本格式）。
4. **路上录、桌面核**：路上用手机单手完成录入；汇总、导入、导出这类重操作留给桌面。
5. **数据是用户的**：可导出、可导入、不做锁定；不引入第三方跟踪。

## Accessibility & Inclusion

用户确认的使用条件（**硬约束**，后续设计必须照顾）：

- **手机为主**（iOS Safari / Android Chrome），桌面偶尔使用；
- **支持基线**：Chrome ≥117 / Edge ≥121 / Firefox ≥121 / Safari ≥17（macOS 与 iOS）—— 见「Capabilities and Constraints」中的 2026-10-08 修订；微信内置浏览器需系统内核满足该基线，旧机型不再在支持范围；
- **需要大字与高对比**：户外光线、年龄偏大的使用者；字号一律用 rem（`html` 基准），以响应用户的浏览器字号偏好；
- **需要单手可操作**：加节点、填总里程、保存这三个关键动作必须在拇指可达区，触摸目标 ≥44px。
