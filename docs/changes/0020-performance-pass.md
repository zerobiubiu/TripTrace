- **状态**：已执行

- **影响范围**：`apps/web/src/App.tsx`（懒加载骨架的预留空间）
- **前置文档**：[0019-hardening-pass.md](0019-hardening-pass.md)

## 背景与方法

先按「先测量、后优化」走：**dev server 上的数字不能作基线**。同一段代码、同样 1200 条行程，dev（未打包 + dev 版 JSX）与生产构建（`bun run build:web` 后用零依赖临时静态服务托管 `dist`）差一个量级：

| 指标 | dev server | 生产构建 |
| --- | --- | --- |
| FCP / LCP | 684 ms | **288 ms** |
| 备注框键入（中位 / 峰值） | 36 ms / 90 ms | **11 ms / 15 ms** |
| 展开 327 行汇总 | 602 ms | **61 ms** |

所以结论以生产构建为准；dev 上的「慢」多数是未打包造成的假象，不进入优化清单（按 optimize 参考：不优化并不慢的东西）。

**取证手段**：omp 的 `browser`（Puppeteer + CDP `Profiler`、`PerformanceObserver`、`performance.getEntriesByType`）。本会话没有 Chrome DevTools MCP，所以 web-perf 技能里的 `performance_start_trace` / `performance_analyze_insight` 不可用，改用等价的 CPU profile 与布局位移观察器；未能采集的是 Lighthouse 的综合评分与真实网络节流。

## 生产基线（1200 条行程、iOS 尺寸视口 390×844）

| 指标 | 实测 | 判定 |
| --- | --- | --- |
| FCP / LCP | 288 ms | 良好（< 1.8 s / < 2.5 s） |
| DOMContentLoaded / load | 120 ms / 120 ms | 良好 |
| JS 传输 | 813 KB（未压缩；线上有 brotli，约 215 KB） | 可接受 |
| 键入延迟（备注框，20 字符） | 中位 11 ms、峰值 15 ms | 良好（≈ 一帧） |
| 切到记录页 | 351 ms（含懒加载块与被测循环的等待） | 主线程长任务仅 **60 ms** |
| 汇总页首绘 | 326 ms（同上） | 同上 |
| 展开 327 行 | 61 ms | 良好 |
| 冷启动长任务 | 51 / 113 / 60 ms | 可接受（本地未节流） |
| 每字符写 localStorage | 20 次（20 字符） | 见「不做的」 |
| **CLS（session window）** | **0.2873（poor，> 0.25）** | **必须修** |

## 瓶颈定位与修复

**CLS 是唯一真实的违规项**，来源单一：懒加载骨架与真实内容高度差太大。

- 观察器给出的位移来源全部是页脚（`SPAN` = 「途迹 TripTrace v…」），每次切页 `top 445 ↔ 0`、`height 44 ↔ 0`；
- 分相实测：**加载相**视图区只有 376 px（3 个骨架）→ 页脚在 **445**（屏内可见）；**加载完成**视图区 6476 px（40 张行程卡）→ 页脚到 **6545**（屏外）。页脚从屏内消失被计为一次布局位移，每次 0.0479，切几次页就累到 0.28。

修法就是 optimize 参考里的「为即将出现的内容预留空间」：给懒加载骨架 `minHeight: 100vh`（`App.tsx` 的 `ViewSkeleton`），使页脚在**加载相已经在折叠线以下**，内容到达时不再移动。

## 执行验证记录

**执行环境**：Windows 10（10.0.26300）· Chrome 141（自动化，`isMobile/hasTouch`）· 生产构建 `dist` 由临时静态服务（:4173，无压缩）托管 · `/api/**` 回放 1200 条行程桩数据。

**A/B 方法**：同一台机器、同一流程（延迟 2.5 s 的 `/api/trips` 制造加载相 → 切到记录页 → 等加载完成 → 再切三次页），对比「骨架自然高度」与「预留 100vh」两种状态；用 `addStyleTag` 原地还原修前状态，避免两次构建带来的差异。CLS 按标准 session window 口径（1 s 间隔、5 s 窗口取最大值）计算。

| 断言 | 修前（骨架自然高度） | 修后（预留 100vh） |
| --- | --- | --- |
| 加载相页脚位置 | top **445**（屏内，844 高视口） | top **913**（折叠线以下）✅ |
| session-window CLS | **0.2873**（poor） | **0.0001**（good）✅ |
| 单次最大位移 | 0.0479（页脚） | ≈ 0 ✅ |

**验证结论**：生产构建下唯一超标的 CWV 指标（CLS 0.287 → 0.0001）已闭环，且是单因、可复现、同机 A/B 证实的修复；其余指标均在良好区间，未做无收益的改动。

## 有意不做（各有量化依据）

1. **草稿的每键一次同步写 localStorage**（20 字符 → 20 次）：生产构建下键入总成本中位 11 ms、峰值 15 ms，收益不足；改成防抖反而会在防抖窗口内退出时**丢掉最后几个字符**，是安全性倒退。
2. **展开超长列表（327 行）**：生产构建 61 ms，无需虚拟滚动或 `content-visibility`。
3. **切页的 326–351 ms**：主线程长任务只有 60 ms，其余是懒加载块的传输与应用外壳重绘；各视图 chunk 只有 1.2–19 KB，收益有限。
4. **首屏 113 ms 长任务**：在本地未节流环境下可接受；低端机需真机复测（见下）。

## 已知限制

- 未做**真实网络节流与低端设备**测试（optimize 参考强调这两点）；本地 1200 条行程的结论不等于低端安卓上的结论。
- 未采集 Lighthouse 综合评分（本会话无对应的 MCP 工具）。
- 桩数据是构造的（1200 条、40 个节点名），真实数据的分布可能不同。
- 预留 100vh 只对「懒加载/加载相」生效，不影响加载后的版式；但**其它来源的位移**（例如内容异步到达时列表自身高度变化）未逐一预留——当前实测这些位移合计已 < 0.01。

## 后续验证建议

1. 线上部署后在真实手机上（含低端安卓）看一次冷启动与切页，用 Chrome UX Report / 真机 Performance 面板复核 CLS 与 INP。
2. 若将来列表首屏仍偏慢，优先考虑把 `PAGE_SIZE`（记录页每页 60 条）下调，而不是上虚拟滚动。
3. 真机复测时顺带确认：慢网（3G）下骨架 → 内容的过渡是否仍无跳动。
