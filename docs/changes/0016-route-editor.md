- 前置文档：[0012-node-editor-dnd.md](0012-node-editor-dnd.md)（节点 id 与拖动）、[0006-entry-rules-nav-and-picker.md](0006-entry-rules-nav-and-picker.md)（分段必填与反向推导）

## 背景

用户以 `/impeccable craft` 要求重构路线编辑交互：

1. **统一结构**：把「路线节点」与「分段里程」融合为一个连续的路线编辑组件，不再是两个独立区域；每个节点有名称控件，相邻节点之间有分段里程控件，增删/重排时里程不错位，保留现有路线计算能力。
2. **移动端先选后输**：点节点名先给候选列表（不弹键盘）→ 选中即完成 → 用户明确选择"输入/搜索"才进文本输入；无候选项可直接输入；输入时模糊匹配、实时结果；输入中列表要合理隐藏或向上展开避免遮挡；处理键盘弹出后的可视区、滚动、焦点、候选项选择与点外关闭。
3. **按使用频率排序候选**：频率越高越靠前；模糊匹配结果里也结合频率；低频/新节点仍可搜到；明确频率统计口径并复用现有存储；无历史时要有合理的初始化/更新机制；**候选顺序不得影响路线的实际顺序**。
4. **约束**：先检查现有组件/数据模型/路线计算/移动端输入逻辑；复用组件库与设计系统；不要只改 CSS；不要造重复且易失同步的状态副本。

改造前现状（取证）：

- `EntryView` 里是**两个区域**：卡片「路线节点（顺序决定路线）」（`NodeEditor` 的行 + 底部一个 `Autocomplete` + 「添加节点」按钮）与卡片「分段里程（每段必填）」——分段是另一张卡、另一处循环，与节点行没有视觉关联。
- 节点名只能整行输入（无"先选后输"的区分）；候选排序已经在 `suggestNodeNames` 里做了"前缀优先 → 包含优先，各自按次数降序"，但**从没写清频率口径**。
- 新增节点要先在底部输入框打字再点按钮；空节点不存在。

## 方案

### 1. 一个组件、一条路线（`components/RouteEditor.tsx`）

一行 = `拖动手柄 + 站号 + 节点名控件 + 移除`，**该行下方紧接「到下一站的里程」**（`A → B` + 里程输入 + 公里）。于是整块从上到下读就是一条路：`家 → 25 → 圣润 → 12 → 天九`。拖动仍是行级排序（手柄是唯一激活器），分段的**显示位置**跟着行，但分段的**归属**永远由相邻端点对决定（`legsForNodes`）——所以拖动后值会跟着路段走，不会跟着行错位。

数据仍只有一份：`EntryForm.nodes` + `EntryForm.legs`，并明确写下**不变量 `legs.length === max(0, nodes.length - 1)`**。新增的 `withNodeAppended`（追加待命名空节点）也走同一条 `legsForNodes` 重建规则。

### 2. 先选后输（`components/NodeNameField.tsx`）

- 默认**选择态**：输入框 `readOnly` + `inputMode: none` → 点一下展开候选，**不唤起软键盘**；点候选即完成（仍不进入输入态）。
- 右侧**键盘图标**（Tooltip「手动输入」）是明确的输入入口；进入输入态后才可敲键盘，placeholder 出现，候选按输入串实时模糊匹配；再点一次回到选择态。
- 候选为空（还没有历史）时，点开即直接进输入态——没有可选项就不该拦着用户打字。
- 选择态给的是**全量常用榜**（查询词为空），输入态才按输入值过滤——这是"先选后输"能成立的关键（否则点开只会看到与当前值完全相同的一项）。
- 弹层 `flip` + `preventOverflow`（各留 8px），且**高度上限跟着视口**（`min(264px, 34vh)`）：软键盘把可视区压到三四百像素时列表仍完整落在屏内且不遮挡字段（MUI 默认的 `40vh` 加纸面内边距实测会溢出 6px）。
- 点击外部由 Autocomplete 关闭；Esc 关闭；方向键/回车选择沿用 MUI 默认。

### 3. 频率口径（复用既有索引，不新增存储）

`lib/suggest.ts` 的 `buildIndex(trips)` 里，每个节点名（归一化 + 小写）统计 **`count` = 包含该节点的行程条数**，`lastDate` = 最近一次出现日期。`suggestNodeNames` 的排序 = 「前缀命中在前、包含命中在后，各层内按 `count` 降序、次数相同按 `lastDate` 降序」。没有历史时索引为空 → 候选为空 → 直接进输入态；保存行程后 `trips` 变化、索引自动重建，**不需要额外存储或迁移**。**候选顺序与应用顺序无关**：路线顺序永远由节点在 `nodes` 数组里的位置决定。

- 验证结论：四条要求逐条实测通过——结构统一、移动端先选后输（不弹键盘）、频率排序（口径明确且与独立复算一致）、复用既有索引与设计系统且不新增状态副本；顺带修掉一个会造成**里程静默丢失**的不变量破坏 bug。
- 已知限制：
  1. "不弹键盘"通过 `readOnly` + `inputMode="none"` 保证（实测属性），`tab.errors` 0 条；**真机软键盘是否弹出未在 iOS/Android 实机上确认**，键盘弹出后的可视区行为用 390×420 视口模拟验证（弹层完整在屏内且不遮挡字段）。
  2. 选择态与输入态是控件内部状态（`useState`），不随草稿持久化——重新打开时回到选择态（符合"先选"的默认）。
  3. 频率只统计**已保存行程**：刚在本表单里命名、尚未保存的组合不会立即进入候选榜（保存后自动生效）。
  4. `.impeccable/design.json` 侧车未重新生成（组件清单未含 `RouteEditor` / `NodeNameField`），需要时跑 `/impeccable document`。
