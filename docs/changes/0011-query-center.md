# 0011 汇总页升级为查询中心、记录页做明细查询（0.8.0）

- 状态：已执行
- 影响范围：`apps/web`（汇总页重写、记录页加筛选、四处共用模块）、`AGENTS.md`（一条查询规则）、文档
- 前置文档：[0009-init-adapt-harden.md](0009-init-adapt-harden.md)、[0010-nav-records-nodes-avatar.md](0010-nav-records-nodes-avatar.md)（已回退，其记录页思路可参考）
- 生效版本：0.8.0
- 不涉及：接口、数据库、部署拓扑（行程仍是一次性拉全量，查询全在前端内存里做）

## 背景

用户要求「加强汇总页的内容，成为一个多功能数据查询中心，功能不要这么单一」，并提出一个方向：**汇总承担集中查询（聚合），记录承担详细条目查询（明细）**。

当时的现状：

- 汇总页（`StatsView`）只能按「年」看四张指标卡 + 月度分布 + 高频路段，维度写死（年 → 月 → 路段），不能换时间范围、不能换视角、不能下钻，也没有缺口提示。
- 记录页（`RecordsView`）只有「最新的 60 条」按月/日分组，没有任何筛选，找某一趟路只能一条条翻。
- 两页各算各的：指标卡用 `computeStats`，记录页自己 reduce 月/日里程——口径没有共同来源。

用户自己的台账习惯（原始文本：`圣润,家 单次25km`、`9.28 … 57 公里`、`203 公里` 小计）说明真正要回答的是两类问题：**「这段时间我跑了多少」**（范围 + 读数）与**「这条路由谁跑过几次、一趟多少公里」**（按路线/分段看频次与单次值）。

## 方案

### 分工

| 页面 | 角色 | 能力 |
| --- | --- | --- |
| 汇总（集中查询） | 聚合视角 | 时间范围 → 读数带 → 四种聚合维度（月份 / 路线 / 分段 / 节点）+ 排序 + 前 10 项展开 → 点某一行带着该行的条件跳到记录页 |
| 记录（明细查询） | 条目视角 | 同一时间范围 + 关键词（节点名或备注）+ 只看未填里程 + 排序（最新在前 / 里程从高到低）+ 结果摘要 + 条件胶囊可逐个移除 + 无匹配时一键清空 |

跨页的桥梁是 `TripFilter`：汇总页每一行自带「这一行对应的筛选」（`drillForRow`），点行即把该筛选交给记录页（`App` 持有 `recordsFilter`），所以「汇总说 6 次 → 记录里就是那几条」这条链路是可核对的，而不是靠人眼对齐。

### 口径（都落在 `lib/query.ts`，两页共用）

- 合计里程只累加 `totalKm` 有值的行程；空的单独计「N 条未填里程」（汇总页是可点击的琥珀胶囊，记录页追加在摘要行尾）。
- 行程次数＝条数；出行天数＝不同日期数；单次均值＝总里程 ÷ **有里程的条数**。
- **分段不分方向**：`家 ⇄ 圣润` 两个方向合成一条（与 PRODUCT.md「同一条路往返里程相同」一致）；分段行的「次数」是分段出现次数，「条行程」是含它的行程数——后者才是下钻看到的条数，所以两个数都写在行上。
- 路线维度按整条节点链分组（键复用 `suggest.ts` 导出的 `routeKey`，补全与聚合同一套键，不会漂移）。

### 界面

- 新增三个共用件：`components/PillGroup.tsx`（胶囊单选组，`aria-pressed` + `role="group"`，可换行）、`components/DateField.tsx`（把填报页那段只读日期字段抽出来，两处共用同一实现）、`components/RangeControl.tsx`（快捷档 + 自定义起止）。
- 汇总页两卡：**查询条件**卡（范围 / 维度 / 排序 + 分隔线下的范围文案、缺里程胶囊与四个读数）+ **结果**卡（标题随维度变：各月份的里程 / 各路线的里程 / 各分段的里程 / 各节点的到达次数，右上角项数，行可点，超过 10 项给「显示全部 N 项」）。
- 记录页：查询条件卡（范围 / 关键词 / 排序 / 里程筛选 / 摘要行 / 条件胶囊）+ 结果（最新在前＝按月/日分组；**里程从高到低＝不再分组**，改成一条榜单并且每条自带日期头——分组会把排序藏起来）。

| 控制台 | 全程 `tab.errors()` | 0 条错误 |

- 体积核算（过程中发现并纠正的度量错误）：入口 chunk 从 530 kB 涨到 583 kB 看似回归，实测**首屏闭包**为 743.17 kB → 747.77 kB，**净增 4.6 kB**；差额来自 Rollup 把 `TextField`/`Button`/`format` 共享块归并回入口（同口径下这些块本来就随首屏加载）。已在 `docs/architecture/0001` 与 `PRODUCT.md` 写明「比体积要量首屏闭包」，避免下次再被这个假回归误导。

- 验证结论：核心读数、四维聚合、下钻链路、明细筛选、排序与两种结果形态在移动/桌面/深色下均通过；聚合数值有独立实现对照，跨页条数口径一致。
- 已知限制：
  1. 数据仍在登录后一次性拉全量（个人量级）；数千条以上需要改成范围查询 + 服务端聚合（见 `docs/architecture/0001` 第 9 节）。
  2. 分段维度按「无序对」合并，若某条路两个方向确实不同里程，行上的「单次」取出现最多的那个值（少数派方向不单独成行）。
  3. 记录页卡片的「编辑 / 删除」在 390px 下会换行（0.6.2 起的既有排版，本次未改）。
  4. 拖动排序、日历查询等 0.7.0 的做法已随 0.7.1 回退，本版没有重新引入。

## 后续验证建议

1. 用真实账号在线上按自己的历史数据核一遍：先在汇总页看某个范围的读数，再下钻到记录页确认条数与合计里程相符。
2. 想再加查询能力（例如按备注关键词、按月对比、金额台账）时：先改 `lib/query.ts`，再让两页共同受益——不要在某一个视图里单独实现。
